## v0.8.4 — released 2026-11-09

### Action required

Remove `endpoints.oslo_db.auth.octavia.password` (`OCTAVIA_DB_PASSWORD`) from `secret-openstack.yaml` in your deploy repo before this change syncs. The chart reaches both Octavia databases with one account and refuses to render when `endpoints.oslo_db.auth.octavia` and `endpoints.oslo_db_persistence.auth.octavia` differ, which is what a leftover password causes. The error reads `endpoints.oslo_db_persistence.auth.octavia must match endpoints.oslo_db.auth.octavia`.

### Deploy repo changes

Horizon's `Database`, `User` and `Grant` resources are now rendered by the chart, with a `Connection` that writes `horizon-db-conn`, instead of coming from `components/horizon/horizon-mariadb-db.yaml`, which is removed.

Unlike the other services, Horizon is a Django application and not an oslo.config service. Its settings still read the database password from `endpoints.oslo_db.auth.horizon.password`, so `HORIZON_DB_PASSWORD` must stay in `secret-openstack.yaml` and must match the `password` in the `horizon-db-password` Secret.

The `horizon-db-password` Secret (`username` and `password` keys) is still read from your deploy repo, and the chart no longer renders it, so it must exist before this change syncs.

Argo CD prunes the old `Grant` named `horizon-grant`; the chart's is named `horizon`. Check that both are Ready after the sync:

```bash
kubectl -n openstack get database,user,grant,connection -l application=horizon
```

The old `horizon-grant` can get stuck terminating. With `privileges: [ALL]` and `grantOption: true`, the operator's finalizer fails on delete with ``Error 1064 ... near 'ON `horizon`.* FROM 'horizon'@'%''`` (seen on mariadb-operator 25.8.4). If `horizon-grant` is still present with a `deletionTimestamp`, revoke the privileges by hand and then remove the finalizer so the object can go away:

```bash
kubectl mariadb -n openstack mariadb -e "REVOKE ALL PRIVILEGES, GRANT OPTION FROM 'horizon'@'%';"
kubectl -n openstack patch grant horizon-grant --type=merge -p '{"metadata":{"finalizers":null}}'
```

Patching the finalizer alone leaves the old grant in the database. The new `horizon` Grant re-applies the privileges for the same account.

Octavia now gets its `[database] connection` and `[task_flow] persistence_connection` from the MariaDB operator instead of from the `OCTAVIA_DB_PASSWORD` Helm value. The chart renders the `Database` resources for `octavia` and `octavia_persistence`, one `User`, a `Grant` for each database and a `Connection` for each, and the operator writes the connection strings into the `octavia-db-conn` and `octavia-persistence-db-conn` Secrets, which are projected into every Octavia workload that talks to the database. `components/octavia/octavia-mariadb-db.yaml` is removed.

The `octavia-db-password` Secret (`username` and `password` keys) is still read from your deploy repo, and the chart no longer renders it, so it must exist before this change syncs. Pods wait for `octavia-db-conn`, so a missing Secret shows up as pods stuck in `ContainerCreating`.

Argo CD prunes the old `Grant` resources named `octavia-grant` and `octavia-grant-persistence`; the chart's are named `octavia` and `octavia-persistence`. Check that all of them are Ready after the sync:

```bash
kubectl -n openstack get database,user,grant,connection -l application=octavia
```

The old grants can get stuck terminating. With `privileges: [ALL]` and `grantOption: true`, the operator's finalizer fails on delete with ``Error 1064 ... near 'ON `octavia`.* FROM 'octavia'@'%''`` (seen on mariadb-operator 25.8.4). If either is still present with a `deletionTimestamp`, revoke the privileges by hand and then remove the finalizers so the objects can go away:

```bash
kubectl mariadb -n openstack mariadb -e "REVOKE ALL PRIVILEGES, GRANT OPTION FROM 'octavia'@'%';"
kubectl -n openstack patch grant octavia-grant --type=merge -p '{"metadata":{"finalizers":null}}'
kubectl -n openstack patch grant octavia-grant-persistence --type=merge -p '{"metadata":{"finalizers":null}}'
```

Patching the finalizers alone leaves the old grants in the database. The new `octavia` and `octavia-persistence` Grants re-apply the privileges for the same account.

## v0.8.0 — released 2026-10-29

### Deploy repo changes

Services are moving to get their `[database] connection` from the MariaDB operator instead of from a `<SERVICE>_DB_PASSWORD` Helm value. For each converted service the chart renders the `Database`, `User`, `Grant` and `Connection` resources, and the operator writes the connection string into the `<service>-db-conn` Secret, which is projected into every workload of that service that talks to the database. The service's `components/<service>/<service>-mariadb-db.yaml` is removed.

Converted so far: Neutron, Placement, Glance, Keystone.

The `<service>-db-password` Secret (`username` and `password` keys) is still read from your deploy repo, and the chart no longer renders it, so it must exist before this change syncs. Pods wait for `<service>-db-conn`, so a missing Secret shows up as pods stuck in `ContainerCreating`.

Argo CD prunes the old `Grant` named `<service>-grant`; the chart's is named `<service>`. Check that both are Ready after the sync:

```bash
SERVICE=neutron  # or placement, glance, keystone
kubectl -n openstack get database,user,grant,connection -l application=$SERVICE
```

The old `<service>-grant` can get stuck terminating. With `privileges: [ALL]` and `grantOption: true`, the operator's finalizer fails on delete with ``Error 1064 ... near 'ON `<service>`.* FROM '<service>'@'%''`` (seen on mariadb-operator 25.8.4). If `<service>-grant` is still present with a `deletionTimestamp`, revoke the privileges by hand and then remove the finalizer so the object can go away:

```bash
SERVICE=neutron  # or placement, glance, keystone
kubectl mariadb -n openstack mariadb -e "REVOKE ALL PRIVILEGES, GRANT OPTION FROM '$SERVICE'@'%';"
kubectl -n openstack patch grant $SERVICE-grant --type=merge -p '{"metadata":{"finalizers":null}}'
```

Set `SERVICE` to each converted service in turn.

Patching the finalizer alone leaves the old grant in the database. The new `<service>` Grant re-applies the privileges for the same account.

`<SERVICE>_DB_PASSWORD` in `secret-openstack.yaml` is no longer used by a converted service and can be removed from your deploy repo once every cluster is on this version.
