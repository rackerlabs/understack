## v0.8.9 — released 2026-11-17

### Deploy repo changes

Nova now gets its `[database] connection` and `[api_database] connection` from the MariaDB operator instead of from the `NOVA_DB_PASSWORD` Helm value. The chart renders the `Database`, `User`, `Grant` and `Connection` resources for the `nova_api`, `nova` (cell1) and `nova_cell0` databases. The operator writes the connection strings into the `nova-db-conn`, `nova-cell1-db-conn` and `nova-cell0-db-conn` Secrets, which are projected into the API, metadata, novncproxy, conductor, scheduler and db-sync workloads. `components/nova/nova-mariadb-db.yaml`, `nova-api-mariadb-db.yaml` and `nova-cell0-mariadb-db.yaml` are removed.

The chart's RabbitMQ topology resources are disabled; `components/nova/nova-rabbitmq-queue.yaml` still manages the RabbitMQ user, vhost, permission and policy.

The `nova-db-password` Secret (`username` and `password` keys) is still read from your deploy repo, and the chart no longer renders it, so it must exist before this change syncs. Pods wait for the `nova-db-conn` Secrets, so a missing Secret shows up as pods stuck in `ContainerCreating`.

The `Database` and `User` resources keep their names (`nova`, `nova-api`, `nova-cell0`), so they are adopted in place. The `Grant` resources are renamed and Argo CD prunes the old ones:

| Database | Old `Grant` | New `Grant` |
| --- | --- | --- |
| `nova_api` | `nova-api-grant` | `nova` |
| `nova` | `nova-grant` | `nova-cell1` |
| `nova_cell0` | `nova-cell0-grant` | `nova-cell0` |

Check that the new ones are Ready after the sync:

```bash
kubectl -n openstack get database,user,grant,connection -l application=nova
```

The old grants can get stuck terminating. With `privileges: [ALL]` and `grantOption: true`, the operator's finalizer fails on delete with ``Error 1064 ... near 'ON `nova`.* FROM 'nova'@'%''`` (seen on mariadb-operator 25.8.4). If any old grant is still present with a `deletionTimestamp`, revoke the privileges by hand and then remove its finalizer so the object can go away:

```bash
kubectl mariadb -n openstack mariadb -e "REVOKE ALL PRIVILEGES, GRANT OPTION FROM 'nova'@'%';"
for grant in nova-grant nova-api-grant nova-cell0-grant; do
    kubectl -n openstack patch grant $grant --type=merge -p '{"metadata":{"finalizers":null}}'
done
```

All three databases share the one `nova` account, so that `REVOKE` removes the privileges on all of them. The new `Grant` resources re-apply them; confirm with `SHOW GRANTS FOR 'nova'@'%'` that all three databases are listed before restarting anything.

`NOVA_DB_PASSWORD` in `secret-openstack.yaml` is no longer used and can be removed from your deploy repo once every cluster is on this version.

Router-flavor definitions are now deployment-owned so sites can customize them through Kustomize. UnderStack no longer supplies the `dynamic-vrf`, `static-vrf`, `svi`, and `pa1410` `NeutronRouterFlavor` resources from `components/openstack-sync-plugins`.

Before upgrading UnderStack:

1. Update your deployment repository to supply the four CRs. In `undercloud-deploy`, they are shared under `hardware/neutron-router-flavors`; reference that directory from each site's `openstack-sync-plugins/kustomization.yaml`:

    ```yaml
    resources:
      - ../../hardware/neutron-router-flavors
      # Keep the site's existing resources here.
    ```

2. Keep the existing CR names, namespace, and specifications unchanged, including `spec.name`, credentials references, and service-profile metadata. Sync the deployment-repository changes before adopting the UnderStack removal. While both sources supply the same CRs, Argo CD may report a temporary `RepeatedResourceWarning`.

3. Upgrade UnderStack and resync the site's OpenStack sync plugins application. Confirm the four CRs remain present with their original UIDs and that the Neutron flavor and service-profile UUIDs and bindings are unchanged.

Do not upgrade UnderStack before the deployment repository supplies these CRs: Argo CD's automatic pruning can otherwise remove them.

## v0.8.5 — released 2026-11-10

### Deploy repo changes

Skyline's `Database`, `User` and `Grant` resources are now rendered by the chart, with a `Connection` that writes `skyline-db-conn`, instead of coming from `components/skyline/skyline-mariadb-db.yaml`, which is removed.

Skyline reads its database settings from its own config rather than from oslo.config, so it still takes the password from `endpoints.oslo_db.auth.skyline.password`. That value must stay in your deploy repo and must match the `password` in the `skyline-db-password` Secret.

Argo CD prunes the old `Grant` named `skyline-grant`; the chart's is named `skyline`. Check that all of them are Ready after the sync:

```bash

```

The old `skyline-grant` can get stuck terminating. With `privileges: [ALL]` and `grantOption: true`, the operator's finalizer fails on delete with ``Error 1064 ... near 'ON `skyline`.* FROM 'skyline'@'%''`` (seen on mariadb-operator 25.8.4). If `skyline-grant` is still present with a `deletionTimestamp`, revoke the privileges by hand and then remove the finalizer so the object can go away:


## v0.8.4 — released 2026-11-09

### Action required

Remove `endpoints.oslo_db.auth.octavia.password` (`OCTAVIA_DB_PASSWORD`) from `secret-openstack.yaml` in your deploy repo before this change syncs. The chart reaches both Octavia databases with one account and refuses to render when `endpoints.oslo_db.auth.octavia` and `endpoints.oslo_db_persistence.auth.octavia` differ, which is what a leftover password causes. The error reads `endpoints.oslo_db_persistence.auth.octavia must match endpoints.oslo_db.auth.octavia`.

### Deploy repo changes

Unlike the other services, Horizon is a Django application and not an oslo.config service. Its settings still read the database password from `endpoints.oslo_db.auth.horizon.password`, so `HORIZON_DB_PASSWORD` must stay in `secret-openstack.yaml` and must match the `password` in the `horizon-db-password` Secret.

Octavia now gets its `[database] connection` and `[task_flow] persistence_connection` from the MariaDB operator instead of from the `OCTAVIA_DB_PASSWORD` Helm value. The chart renders the `Database` resources for `octavia` and `octavia_persistence`, one `User`, a `Grant` for each database and a `Connection` for each, and the operator writes the connection strings into the `octavia-db-conn` and `octavia-persistence-db-conn` Secrets, which are projected into every Octavia workload that talks to the database. `components/octavia/octavia-mariadb-db.yaml` is removed.

With `privileges: [ALL]` and `grantOption: true`, the operator's finalizer fails on delete with ``Error 1064 ... near 'ON `octavia`.* FROM 'octavia'@'%''`` (seen on mariadb-operator 25.8.4). ## v0.8.0 — released 2026-10-29

### Deploy repo changes

Services are moving to get their `[database] connection` from the MariaDB operator instead of from a `<SERVICE>_DB_PASSWORD` Helm value. For each converted service the chart renders the `Database`, `User`, `Grant` and `Connection` resources, and the operator writes the connection string into the `<service>-db-conn` Secret, which is projected into every workload of that service that talks to the database. The service's `components/<service>/<service>-mariadb-db.yaml` is removed.

Converted so far: Neutron, Placement, Glance, Keystone.

The `<service>-db-password` Secret (`username` and `password` keys) is still read from your deploy repo, and the chart no longer renders it, so it must exist before this change syncs. Pods wait for `<service>-db-conn`, so a missing Secret shows up as pods stuck in `ContainerCreating`.

Argo CD prunes the old `Grant` named `<service>-grant`; the chart's is named `<service>`. Check that both are Ready after the sync:

```bash
SERVICE=neutron  # or placement, glance, keystone
kubectl -n openstack get database,user,grant,connection -l application=$SERVICE
```

The old `<service>-grant` can get stuck terminating. With `privileges: [ALL]` and `grantOption: true`, the operator's finalizer fails on delete with ``Error 1064 ... near 'ON `<service>`.* FROM '<service>'@'%''`` (seen on mariadb-operator 25.8.4). If `<service>-grant` is still present with a `deletionTimestamp`, revoke the privileges by hand and then remove the finalizer so the object can go away:

```bash
SERVICE=neutron  # or placement, glance, keystone
kubectl mariadb -n openstack mariadb -e "REVOKE ALL PRIVILEGES, GRANT OPTION FROM '$SERVICE'@'%';"
kubectl -n openstack patch grant $SERVICE-grant --type=merge -p '{"metadata":{"finalizers":null}}'
```

Set `SERVICE` to each converted service in turn.

Patching the finalizer alone leaves the old grant in the database. The new `<service>` Grant re-applies the privileges for the same account.

`<SERVICE>_DB_PASSWORD` in `secret-openstack.yaml` is no longer used by a converted service and can be removed from your deploy repo once every cluster is on this version.
